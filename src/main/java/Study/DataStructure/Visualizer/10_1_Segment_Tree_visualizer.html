세그먼트 트리(Segment Tree)

합 세그먼트 트리 + build/query/update 시각화

📖 세그먼트 트리 학습 노트 (클릭해서 펼치기)

🌲 세그먼트 트리란

  • 노드마다 구간 집계값(합, min, max 등)을 저장하는 이진 트리
  • 루트는 [0, n-1], 자식은 [start, mid]와 [mid+1, end], 리프는 원소 하나짜리 구간
  • 부모 = 왼쪽 자식 + 오른쪽 자식, mid = start + (end - start) / 2 (오버플로 방지)

🤔 필요한 이유

방식 query update
배열 순회 O(n) O(1)
누적합 배열 O(1) O(n)
세그먼트 트리 O(log n) O(log n)

값 변경과 구간 조회가 둘 다 많을 때 사용, 값이 안 바뀌면 누적합으로 충분

📦 배열 표현과 4n

  • 루트를 1번으로 잡으면 자식은 node * 2, node * 2 + 1
  • 마지막 레벨이 빈틈없이 채워지지 않을 수 있어, 힙과 달리 인덱스가 0~n-1에 딱 맞지 않음
  • 높이는 ceil(log2 n), 가장 깊은 리프 인덱스는 최대 2^(높이+1) - 1 -> n이 2의 거듭제곱보다 조금만 커도 4n에 근접
  • 3n으로 잡으면 n=36에서 마지막 인덱스 113, 배열 길이 108 -> ArrayIndexOutOfBounds, 안전한 4n이 관례
  • 입력이 int여도 합은 long 배열에 저장해서 오버플로 방지
⚙️ 핵심 연산

🏗 build -> O(n)

  • 리프는 arr[start]를 저장하고 return
  • 왼쪽, 오른쪽 자식을 먼저 재귀로 채운 뒤(후위 순서) 부모를 계산
  • 노드마다 한 번씩만 방문, arr 구간을 다시 합산하면 O(n log n)이 됨

🔍 query(left, right) -> O(log n)

  • 분기 1 겹치지 않음 (left > end || right < start) -> 항등원 반환
  • 분기 2 완전 포함 (left <= start && end <= right) -> tree[node] 반환
  • 분기 3 일부만 겹침 -> 양쪽 자식을 같은 (left, right)로 호출해 합침
  • 겹침 검사를 먼저, 포함 검사를 나중에, 리프는 분기 1 또는 2로 반드시 끝남

✏️ update(idx, v) -> O(log n)

  • idx <= mid면 왼쪽, 아니면 오른쪽 한쪽 자식으로만 내려감 (경로가 한 줄)
  • 리프(start == end)에 도달하면 그 원소가 idx이므로 값만 교체
  • 복귀하며 경로 위 노드만 두 자식의 합으로 재계산

🔎 방문 노드가 레벨당 상수인 이유

  • 분기 3은 질의 경계(left 또는 right)를 노드 구간이 가로지를 때만 발생
  • 같은 레벨의 구간은 서로 겹치지 않아 경계마다 최대 1개 -> 레벨당 분기 3은 최대 2개, 방문은 최대 4개
  • 예시 [2, 5, 1, 4, 3, 6]의 query(1, 4) = [1..1]=5 + [2..2]=1 + [3..4]=7 = 13

🎯 차이를 더하지 않고 두 자식으로 재계산하는 이유

  • 합은 역연산(뺄셈)이 있어 -old +new로 한 원소의 기여분만 갈아끼울 수 있음
  • min은 역연산이 없고 노드가 결과만 들고 있어 어느 원소가 그 값을 만들었는지 알 수 없음
  • 예시: [2, 5] 노드의 min = 2, arr[0]을 9로 바꾸면 차이 +7을 더해 9가 되지만 실제는 min(9, 5) = 5
  • 핵심은 순서가 아니라 집계 결과에서 한 원소의 영향을 되돌릴 수 있는가 (재계산 방식은 결합법칙만 있으면 성립)
  • 펜윅 트리는 += delta 방식이라 합, XOR에 자연스럽고 min, max에는 제약이 붙음
🧩 확장과 선택

🔄 연산 확장

  • 현재 구현은 합 전용, 연산이 고정된 곳은 합치는 식 3곳(build, doUpdate, doQuery 분기 3)과 항등원 1곳(분기 1)
  • 합 0 / 곱 1 / min Long.MAX_VALUE / max Long.MIN_VALUE / gcd 0 / XOR 0
  • 일반화: 생성자에서 LongBinaryOperator op, long identity 주입
  • 중앙값은 결합법칙이 성립하지 않아 불가, 행렬 곱은 왼쪽, 오른쪽 순서를 지켜야 함

📊 누적합과의 선택 기준

  • n = 10만, 쿼리 1만 + 업데이트 1만이면 누적합은 업데이트만 약 10억 연산, 세그먼트 트리는 1만 x 약 17
  • 업데이트가 없다면 누적합이 더 빠르고 가벼움 (n칸 vs 4n칸)
  • 실무 백엔드에서 직접 구현할 일은 드묾 (DB 인덱스, 집계 쿼리, Redis가 담당), 코딩테스트 구간 쿼리의 핵심 도구

🛡 범위 검증

  • update는 0 <= idx <= n-1이 아니면 예외 (idx == n은 마지막, 음수는 첫 원소를 조용히 덮어씀)
  • query는 음수, left > right, 배열 범위 초과를 예외 처리 (없으면 분기 1, 2가 걸러서 일부만 계산된 값이 반환됨)
